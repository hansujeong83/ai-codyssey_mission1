# Mission 1 기술 개념 정리 및 평가자 안내

이 문서는 과제에서 요구한 핵심 개념을 실제 명령과 연결해 설명합니다. 실행 결과를 꾸며 쓰지 않으며, 실제 PC에서 생성된 로그와 캡처만 제출 증거로 사용합니다.

## 1. 절대 경로와 상대 경로

- 절대 경로: 파일 시스템의 기준점부터 목적지까지 전체 경로입니다. 예: `/home/student/codyssey/app/index.html`
- 상대 경로: 현재 작업 디렉터리를 기준으로 한 경로입니다. 예: `app/index.html`, `../README.md`
- `pwd`는 현재 디렉터리를 확인하고, `cd ..`는 부모 디렉터리로 이동합니다.
- 스크립트에서 `$(pwd)`를 사용하면 현재 위치를 기준으로 한 절대 경로를 얻을 수 있습니다. 프로젝트 루트 안에서만 실행되는 명령에는 `./app` 같은 상대경로가 간단하고 이식성이 좋습니다. 반대로 cron, 서비스 설정, 실행 위치가 일정하지 않은 스크립트에는 `/home/student/project/app`처럼 절대경로를 쓰면 기준 위치가 달라져도 대상을 정확히 지정할 수 있습니다. Docker bind mount의 호스트 경로는 절대경로로 전달하는 편이 안전하므로 `$(pwd)/app` 형태를 사용합니다.

## 2. Linux 파일 권한

권한은 소유자(owner), 그룹(group), 기타 사용자(others) 순서로 표시합니다.

| 숫자 | 권한 | 의미 |
|---|---|---|
| 4 | r | 읽기 |
| 2 | w | 쓰기 |
| 1 | x | 실행(파일) 또는 탐색(디렉터리) |

각 사용자 범위의 숫자는 권한 값을 더해 표현합니다.

- `chmod 644 file.txt`: 소유자 읽기/쓰기(6), 그룹 읽기(4), 기타 읽기(4)
- `chmod 755 script.sh`: 소유자 전체 권한(7), 그룹과 기타는 읽기/실행(5)
- `chmod 750 directory`: 소유자는 읽기/쓰기/탐색, 그룹은 읽기/탐색, 기타 사용자는 접근 권한 없음

디렉터리에서 실행(x)은 프로그램 실행이 아니라 디렉터리 내부 항목을 탐색할 수 있는 권한입니다.

## 3. Docker 이미지와 컨테이너

- 이미지(image)는 컨테이너를 생성하기 위한 읽기 전용 템플릿입니다.
- 컨테이너(container)는 이미지로부터 만들어져 실행되는 격리된 프로세스 환경입니다.
- 하나의 이미지로 여러 컨테이너를 실행할 수 있습니다.
- `docker build`는 Dockerfile을 읽어 이미지를 만들고, `docker run`은 이미지로 컨테이너를 생성·실행합니다.
- `docker ps`는 실행 중인 컨테이너, `docker ps -a`는 종료된 컨테이너까지 보여줍니다.

## 4. Dockerfile 커스텀 포인트

이 저장소는 `nginx:1.27-alpine`을 베이스 이미지로 사용합니다.

| 명령 | 목적 |
|---|---|
| `FROM nginx:1.27-alpine` | 경량 NGINX 베이스 이미지 선택 |
| `LABEL` | 이미지의 제목과 설명 메타데이터 기록 |
| `COPY app/ ...` | 직접 만든 정적 웹 페이지를 웹 루트에 복사 |
| `EXPOSE 80` | 컨테이너가 사용하는 웹 포트를 문서화 |
| `HEALTHCHECK` | 컨테이너 내부 HTTP 응답을 주기적으로 확인 |

`EXPOSE`만으로 호스트에서 접속할 수 있는 것은 아닙니다. 호스트 포트와 컨테이너 포트를 연결하는 `-p` 옵션이 필요합니다.

## 5. 포트 매핑과 네트워크

`-p 18080:80`은 호스트의 18080 포트로 들어온 요청을 컨테이너의 80 포트로 전달합니다.

- 호스트 포트: 내 PC에서 브라우저 또는 curl이 접속하는 포트
- 컨테이너 포트: 컨테이너 안의 NGINX가 수신하는 포트
- 브라우저 검증 주소: `http://localhost:18080`

호스트 포트는 다른 프로그램이 이미 사용 중이면 바꿔야 합니다. 예를 들어 `-p 18082:80`으로 변경하면 접속 주소도 `http://localhost:18082`가 됩니다.

## 6. 바인드 마운트와 named volume

| 구분 | 바인드 마운트 | Docker named volume |
|---|---|---|
| 저장 위치 | 사용자가 지정한 호스트 경로 | Docker가 관리하는 저장 공간 |
| 주요 목적 | 개발 중 소스 변경 즉시 반영 | 컨테이너를 교체해도 데이터 보존 |
| 예시 | `$(pwd)/app:/usr/share/nginx/html` | `codyssey-data:/data` |

바인드 마운트는 호스트에서 파일을 직접 편집하고 변경 사항을 즉시 확인하기 쉬운 대신, 호스트 경로와 파일 권한에 영향을 받습니다. named volume은 Docker가 저장 위치를 관리해 데이터베이스나 업로드 파일처럼 컨테이너를 교체해도 남겨야 하는 데이터에 적합하지만, 호스트에서 파일을 직접 찾아 편집하기는 상대적으로 불편합니다. 바인드 마운트 실습은 호스트의 HTML 파일을 수정한 뒤 컨테이너 웹 응답에 변경 문구가 나타나는지 확인합니다.

볼륨 영속성 실습은 첫 컨테이너에서 파일을 기록하고 컨테이너를 삭제한 뒤, 같은 named volume을 연결한 두 번째 컨테이너에서 파일을 다시 읽습니다. 데이터가 유지되면 컨테이너의 수명주기와 데이터 저장소가 분리되었음을 확인한 것입니다.

## 7. Git과 GitHub

- Git: 로컬 저장소에서 변경 이력(commit)을 관리하는 버전 관리 도구입니다.
- GitHub: Git 저장소를 원격에 보관하고 협업·검토·자동화 기능을 제공하는 서비스입니다.
- `git status`: 현재 변경 상태 확인
- `git add`: 커밋할 변경 선택
- `git commit`: 로컬 변경 이력 저장
- `git push`: 로컬 커밋을 원격 저장소로 전송
- `git pull`: 원격 변경을 가져와 현재 브랜치에 통합

인증 토큰, 비밀번호, 개인키는 소스 파일·README·로그·스크린샷에 기록하지 않습니다. GitHub 로그인 화면이나 VS Code 연결 화면을 캡처할 때도 인증 정보가 보이지 않도록 합니다.

## 8. 컨테이너 종료와 유지

- `docker stop NAME`: 실행 중인 컨테이너를 정상 종료합니다. 컨테이너 객체는 남습니다.
- `docker start NAME`: 종료된 컨테이너를 다시 실행합니다.
- `docker rm NAME`: 컨테이너 객체를 삭제합니다.
- `docker exec -it NAME sh`: 실행 중인 컨테이너 안에서 새 명령 프로세스를 시작합니다.
- `docker attach NAME`: 컨테이너의 주 프로세스 입출력에 연결합니다. 터미널에서 분리하는 방식에 주의해야 합니다.

컨테이너를 삭제해도 별도로 연결한 named volume은 삭제되지 않는 한 남습니다.

## 9. 실행 및 증거 생성 순서

저장소 루트에서 다음 명령을 실행합니다.

```bash
bash scripts/capture_mission1.sh
```

스크립트는 현재 PC에서 실행한 명령과 출력을 `docs/evidence/terminal-session.txt`에 기록합니다. Docker 엔진에 연결할 수 없으면 Docker 관련 검증을 완료한 것으로 표시하지 않고 중단합니다.

실행 후 다음을 확인합니다.

```bash
grep -E '\\[PASS\\]|\\[FAIL\\]|RESULT=' docs/evidence/terminal-session.txt
git status --short
```

스크린샷은 실제 화면을 직접 캡처해 `docs/evidence/`에 저장합니다. README의 증거 표에 있는 파일명과 내용 기준을 따르며, 예시 이미지나 합성 화면을 실행 증거로 사용하지 않습니다.
